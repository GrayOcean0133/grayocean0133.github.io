# 应急实战:一次校园网木马的持久化、隐蔽与对抗

> 本章基于一次**真实**校园网应急事件改编,采用**蓝队(防御)视角**。
> 进攻侧只讲**逻辑与原理**(配示意图),不给出任何可运行的攻击代码;防守侧给出**完整可用**的检测与清除代码。
> 所有主机操作请仅在**你拥有或获明确授权**的设备上进行。

## 1 引子:一个"杀不死"的病毒

故事从一台普通的学生电脑开始。这台机装了杀软(火绒),可它**连续多天、每天多次**报同一个毒,并且**反复复发**:

```text
病毒:Trojan/BAT.Runner.bm
路径:C:\Windows\uVgppth.bat          ← 每次文件名都不一样(随机)
触发:cmd.exe /c C:\Windows\<随机>.bat
父进程:...\Chrome\...\elevation_service.exe
```

与此同时,网络防护一直在拦截外联:

```text
svchost.exe / sihost.exe / LogonUI.exe 访问【www.ic978y.com】已阻止   (分类:木马盗号)
```

任何一个做过应急的人,看到这里都会产生一个核心疑问:

> **杀软明明"已处理",为什么病毒还天天回来?**

答案是本章的主线,也是理解一切高级威胁的钥匙:

> **关键认知:杀软删掉的是"症状"(被释放出来的文件),而不是"根"(不停生成这些文件的源头)。只要根还在,症状就会无限再生。**

应急的目标因此变得清晰——**不要追着症状跑,要顺着症状找到根,再从根上铲除。**

## 2 攻防全景图

在深入每个细节前,先建立一张全景。把这张图记住,后面每一节都是在放大它的某一块。

```text
【感染】官网下载被劫持(MITM) → 拿到"真签名软件 + 木马"的捆绑包
            │
【落地】释放到 C:\ESD\... 隐藏目录(真软件做掩护,木马藏在旁边)
            │
【持久化】注册一个 SYSTEM 权限的开机自启服务 ①
            │
【拉起】 服务① ──▶ 木马本体② ──┬──▶ 释放"看门狗"脚本③(防止被杀)
                                └──▶ 把外联模块注入到正版系统进程
            │
【外联】 被注入的 svchost / LogonUI 等 ──▶ 加密回连境外 C2
            │
【目的】 阶段一:窃取账号密码(已证实)   阶段二:留后门待勒索(风险)

  "赖着不走" = 服务①↔看门狗③ 互相复活
  "藏得很深" = 真签名掩护 + 注入正版进程 + 借提权组件 + 命令混淆
```

整个对抗,可以浓缩成两组对立的逻辑:

| 攻击者要的 | 防御者要的 |
| --------- | --------- |
| **持久**:开机自启 + 互保,杀不死 | **断根**:找到并按正确顺序拆掉所有持久化点 |
| **隐蔽**:藏在可信外壳里,不被发现 | **现形**:抓住它"必须留下的痕迹" |
| **权限**:拿到 SYSTEM,为所欲为 | **遏制**:最小权限、阻断提权路径 |
| **通联**:与 C2 保持心跳,偷数据/收指令 | **阻断**:在网络层切断 C2,封堵 IOC |

> **本章的讲法**:每一节先讲**攻击方的逻辑**(它想干什么、凭什么能做到),再讲**防御方的逻辑与代码**(它留下了什么痕、我们怎么抓和清)。

## 3 持久化:恶意 Windows 服务

### 3.1 攻击逻辑:为什么选"服务"

攻击者落地后第一件大事,是解决"**重启之后我还在吗**"的问题,这叫**持久化(Persistence)**。Windows 上能做持久化的地方很多(启动项、计划任务、WMI 订阅……),而本案选择了**最稳的一种:注册成系统服务**。原因有三:

1. **开机自启**:服务可设为 `AUTO_START`,系统一启动它就被拉起,早于用户登录。
2. **最高权限**:服务默认以 `LocalSystem`(即 SYSTEM)身份运行,这是 Windows 上权限最高的账户,比管理员还高,能动几乎所有东西。
3. **形态自由**:正规服务程序需要实现"服务控制接口",但攻击者用一个小技巧绕过——把服务的启动命令写成"**用 cmd 去启动一个普通 exe**"的形式。这样任意一个普通木马 exe 都能被服务拉起来,不必写成标准服务。

本案这个服务的真实面貌(脱敏后):

```text
服务名      : 9gCLChmjG9Dk0Tww2YCm4      ← 随机生成的乱码名
启动类型    : AUTO_START                 ← 开机自启
运行账户    : LocalSystem                ← SYSTEM 最高权限
启动命令    : cmd /c cd /d "<隐藏目录>" && start "" "<随机名>.exe"
```

> **攻击者的小心机:服务名是每台机随机生成的。** 这是为了对抗"用一个固定名字去全网封杀"——你在 A 机看到的名字,在 B 机大概率不一样。这条性质对防御策略影响极大(见 3.3)。

### 3.2 防御逻辑:抓"行为",而不是抓"名字"

既然名字随机、不可枚举,防御就**不能靠匹配固定名字**,而要靠**匹配行为特征**。这个木马服务有一个非常稳定、且正常软件几乎不会出现的特征组合:

> **一个以 `LocalSystem` 运行的服务,它的启动命令是"用 cmd /c 去 start 一个 exe"。**

正常的系统服务,启动路径都是直接指向一个 exe(可能带参数),**极少**有人用 `cmd /c ... start` 这种"脱壳启动"方式。所以这个组合本身就是高可信度的告警信号。

### 3.3 防御代码:检测与清除

```powershell
# ── 检测:列出所有"用 cmd/c 拉起 exe"的 SYSTEM 自启服务 ──
# (通用特征,不依赖随机服务名,可套用到任意一台机器)
Get-CimInstance Win32_Service | Where-Object {
    $_.StartName -eq 'LocalSystem' -and
    $_.PathName  -match 'cmd(\.exe)?\s+/[ck]' -and
    $_.PathName  -match '\bstart\b'
} | Select-Object Name, State, StartMode, PathName | Format-List

# ── 查看某个可疑服务的完整配置(确认启动路径指向哪) ──
sc.exe qc <服务名>

# ── 清除:停止并删除该服务 ──
sc.exe stop   <服务名>
sc.exe delete <服务名>
```

> **注意**:删服务只是断掉"开机自启"这一条线。它还有"看门狗"在保护(见第 4 节),所以**清除必须按正确顺序进行**,否则边删边复活。

## 4 看门狗:进程互保机制

### 4.1 攻击逻辑:让"杀进程"失效

攻击者很清楚,管理员或杀软迟早会"杀掉木马进程"。为了对抗这一点,它部署了**看门狗(Watchdog)**——一个极简的循环脚本,专门盯着木马本体:

```text
看门狗脚本的逻辑(自然语言描述,非代码):
  循环:
    1. 查一下"木马本体进程"还在不在?
    2. 如果【不在了】(说明被杀了) → 立刻把那个服务重新启动起来 → 退出
    3. 如果【还在】 → 睡 10 秒,回到第 1 步
```

于是攻击者构造出一个**互保闭环**,这是它"杀不死"的真正原因:

```text
   服务① ──启动──▶ 木马本体②进程 ──释放并运行──▶ 看门狗③脚本
     ▲                                                  │
     │                                  每10秒检查本体是否存活
     └────────────  本体一旦被杀,立即"重启服务" ◀────────┘
```

- 你只杀进程②:看门狗③发现它没了 → 重启服务① → 服务①又拉起②。复活。
- 你只删脚本③:本体②还在运行,转头又释放一个新的随机名看门狗。复活。
- 你只删服务①:本体②可能还在内存里跑,看门狗③下一秒又试图启动服务(虽然失败,但本体仍在)。

> **关键认知:面对互保结构,"清除顺序"比"清除动作"更重要。** 必须先掐断"复活"的源头(服务),再清理本体和看门狗,最后重启清内存。顺序错了,等于一边救火一边浇油。

### 4.2 防御逻辑与代码:识别看门狗痕迹

看门狗脚本被释放在 `C:\Windows\` 根目录下,文件名随机、体积极小(只有一两百字节)。正常情况下 `C:\Windows\` 根目录**不应该有**这种随机名小脚本。

```powershell
# ── 检测:C:\Windows 根目录下的可疑小 bat(正常系统几乎没有) ──
Get-ChildItem 'C:\Windows\*.bat' -File |
    Where-Object Length -lt 500 |
    Select-Object Name, Length, LastWriteTime

# ── 同时排查正在运行的"看门狗式" cmd 进程(循环跑某个随机 bat) ──
Get-CimInstance Win32_Process -Filter "Name='cmd.exe'" |
    Where-Object { $_.CommandLine -match '/c\s+C:\\Windows\\[A-Za-z0-9]{3,14}\.bat' } |
    Select-Object ProcessId, CommandLine
```

正确的清除顺序(本案实际采用):

```text
① 先删服务      sc delete <服务名>        ← 掐断"重启"源头
② 杀本体与看门狗 Stop-Process              ← 停掉正在跑的进程
③ 删看门狗脚本   Remove-Item C:\Windows\随机.bat
④ 删木马目录     Remove-Item C:\ESD\... -Recurse
⑤ 重启系统                                  ← 清掉内存里的注入(见第6节)
```

## 5 混淆:对抗"按字符串查杀"

### 5.1 攻击逻辑

杀软的一种基础查杀方式是**特征字符串匹配**:看到脚本里有 `tasklist`、`sc start` 这种敏感命令就报警。攻击者用**命令混淆**来破解这一招——在命令中间插入大量"会被命令行解释器吞掉"的转义字符。

效果是:**人和解释器看到的是原命令,而按字符串匹配的杀软看到的是一堆被打断的碎片**,匹配不上,于是漏过。这类手法统称混淆(Obfuscation),常见形式还有反引号、`%` 变量拼接、Base64 编码、超长字符串拼接等。

> **攻击者的目标**:让"语义不变"的同时"字面改变"。语义不变才能正常执行,字面改变才能骗过字符串匹配。

### 5.2 防御逻辑与代码:先"还原"再判读

防御者的应对很直接——**先去混淆(de-obfuscate),把它还原成人类可读的原始命令,再做判断**。这是恶意脚本分析的基本功。

```powershell
# ── 还原被 ^ 混淆的 bat:去掉转义字符即可看到真实命令 ──
(Get-Content '可疑.bat' -Raw) -replace '\^', ''

# ── 还原 Base64 编码的 PowerShell 命令(常见于 -EncodedCommand) ──
$b64 = '<粘贴可疑的Base64串>'
[System.Text.Encoding]::Unicode.GetString([Convert]::FromBase64String($b64))
```

> **经验法则**:凡是看到满屏插入符、反引号、`%xx%`、超长 Base64、字符串拼接——先假设它在混淆,**还原之后再判读**。混淆本身就是一个强烈的"可疑"信号。

## 6 进程注入:藏身与隐蔽外联

### 6.1 攻击逻辑:把自己"寄生"进正版进程

这是本案最值得讲透的一环,也是它能"以系统进程名义偷偷外联"的根本。

防御者一开始很困惑:日志显示是 `svchost.exe`、`sihost.exe`、连登录界面的 `LogonUI.exe` 在访问境外恶意域名。可这些都是 Windows 自带的、有微软正版签名的核心进程,难道被替换了?

排查后发现:**这些进程的二进制文件签名完好、是正版**,系统也**没有**被设置恶意代理或恶意 DNS。三条线索合起来,只剩一个解释——**进程注入(Process Injection)**:

> 木马本体把自己的"外联模块"(一段代码)**塞进这些正版进程的内存里,并让它在目标进程内运行**。运行起来后,这段代码发出的网络请求,在系统看来就是"svchost 在联网",身份完全是正版进程的。

它的逻辑示意:

```text
木马本体②(SYSTEM权限)
   │  枚举系统里长期存活的正版进程
   ▼
选定宿主:svchost / sihost / ctfmon / LogonUI / 浏览器提权服务 ...
   │  把"外联模块"写入宿主进程内存,并在宿主内启动一个线程运行它
   ▼
宿主进程(看起来完全正常)── 在内部 ── 向境外 C2 发心跳
```

攻击者为什么这么做?三个收益:

1. **伪装**:进程列表里全是正版微软进程,流量也算在它们头上,绕过"按进程信誉"的检测。
2. **冗余**:注入到多个进程,杀掉一个还有别的在跑。
3. **早启动**:连登录界面的 `LogonUI` 都被注入 → **开机、还没进桌面就已经在外联**。

> **关键认知:注入是"内存级"的寄生。** 磁盘上那些正版进程的文件一个字节都没改——所以**只查文件、只比签名,永远发现不了它**。这也解释了为什么"删完文件还必须重启":文件清了,但已经注入到内存里的线程,要等宿主进程随重启结束才会消失。

### 6.2 防御逻辑与代码

注入虽然藏在内存,但它**必然在系统层面留下行为痕迹**:有进程在"打开别的进程、往里写可执行内存、在别的进程里起线程"。这些动作可以被审计工具(如微软官方的 **Sysmon**)记录下来。

防御抓手有三层:

**第一层:行为日志(Sysmon)。** 部署 Sysmon 后,重点关注两类事件:

| Sysmon 事件 | 含义 | 为什么可疑 |
| ---------- | ---- | --------- |
| EventID 8 (CreateRemoteThread) | 一个进程在另一个进程里创建了线程 | 正常软件极少这么做;注入的标志性动作 |
| EventID 10 (ProcessAccess) | 一个进程申请了对另一进程的高权限句柄 | 注入的前置步骤(打开目标进程) |

```powershell
# ── 从 Sysmon 日志中筛出"跨进程创建远程线程"事件(注入强信号) ──
# 用 -FilterHashtable 在日志端过滤,比"全部取回再 Where-Object"快得多
Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    Id      = 8
} -MaxEvents 50 | Select-Object TimeCreated, Message
```

**第二层:网络反证。** 既然注入是为了外联,那就反过来看——**哪些"本不该联网"的系统进程在联网?** 这是非常有效的旁证。

```powershell
# ── 列出有外网连接的进程,人工审视:LogonUI/sihost 这类出现在这里就极可疑 ──
Get-NetTCPConnection -State Established |
    Where-Object { $_.RemoteAddress -notmatch '^(0\.|127\.|10\.|169\.254\.|172\.(1[6-9]|2\d|3[01])\.|192\.168\.|::1?$|fe80|f[cd])' } |
    ForEach-Object {
        $p = Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue
        [PSCustomObject]@{
            Proc   = $p.ProcessName
            PID    = $_.OwningProcess
            Remote = "$($_.RemoteAddress):$($_.RemotePort)"
        }
    } | Sort-Object Proc | Format-Table -AutoSize
```

**第三层:清除靠重启。** 注入在内存里,**断根(删服务/本体)之后必须重启**,让被注入的宿主进程结束、重建,内存里的恶意线程随之消失。重启后再复查(服务、看门狗、外联)三项是否归零,才算闭环。

> **防御逻辑总结**:文件层比签名查不出注入;要靠**行为层(Sysmon 跨进程操作)**和**网络层(异常进程外联)**两个旁证锁定它,靠**重启**清除它。

## 7 父进程"漂白":一次"是不是 0day"的辨析

### 7.1 现象

日志里那些 `cmd /c <随机>.bat`(看门狗)的**父进程,显示为浏览器的 `elevation_service.exe`**(Chrome/Edge 都有)。`elevation_service` 是浏览器用来做"自动更新提权"的、以 SYSTEM 运行的可信组件。一个恶意脚本"出自"可信的微软/谷歌组件,看起来很可疑——这是不是利用了某个 0day?

### 7.2 它是 0day 吗?——不是,而这正是个好问题

先明确定义:**0day 是厂商尚不知道、没有补丁的未知漏洞。** 本案这个现象几乎可以确定**不是漏洞利用**,三条理由:

1. **它不需要靠这个提权**。木马通过恶意服务**已经是 SYSTEM**。一个已经拥有最高权限的程序,没有动机再去"利用浏览器提权"——提权漏洞的前提是"当前权限不够"。
2. **`elevation_service.exe` 经验证是正版有效签名**,没被替换或打补丁绕过。
3. **"父进程是 elevation_service"有两个完全已知、无需任何漏洞的解释:**
   - **进程注入的副作用(更可能)**:第 6 节已确认木马注入进了 `elevation_service`。注入进去的代码**在该进程内部**启动 cmd/bat,那 cmd 的父进程自然就显示成 `elevation_service`。这是注入的结果,不是利用。
   - **父进程伪造(Parent PID Spoofing,`T1134.004`)**:Windows 提供**合法 API**允许创建进程时指定任意父进程,木马借它把恶意进程"挂"在可信进程名下做伪装。这是被滥用的**合法功能**,不是漏洞。

> **关键认知:90% 看起来"不可思议"的现象,查到底都是已知技术(TTP)的组合。** 养成习惯:**先用已知技术解释,排除干净了再考虑 0day**。轻易喊 0day,往往是分析没做到位。

### 7.3 防御逻辑与代码:抓"反常的父子关系"

不管是注入副作用还是父进程伪造,它都留下一个**正常情况下绝不会出现的父子关系**:`elevation_service.exe` 居然有个 `cmd /c 随机.bat` 的子进程。正常浏览器更新组件永远不会去跑 `C:\Windows\` 下的随机脚本。这就是一条高可信度告警规则。

```powershell
# ── 检测:浏览器提权服务是否有"cmd/脚本"类异常子进程 ──
# 先把进程快照成 PID→进程 哈希表,避免对每个进程再查一次 CIM(慢,且 PID 可能被复用导致误判)
$procs = Get-CimInstance Win32_Process
$byId  = @{}
$procs | ForEach-Object { $byId[[uint32]$_.ProcessId] = $_ }

$susParents = @('elevation_service.exe')   # 可信但易被滥用的父进程(数组,便于扩充)
$shells     = @('cmd.exe','powershell.exe','pwsh.exe','wscript.exe','cscript.exe','mshta.exe')

$procs | Where-Object {
    $shells -contains $_.Name -and
    $susParents -contains $byId[[uint32]$_.ParentProcessId].Name
} | Select-Object ProcessId, Name, CommandLine, ParentProcessId | Format-List
```

> 在 Sysmon 里,这对应 **EventID 1(进程创建)** 的父子关系审计——把"可信进程突然生出脚本解释器"做成告警,是性价比极高的检测规则。

## 8 C2 与外联:盗号与留后门

### 8.1 攻击逻辑

木马的最终目的要靠**与攻击者服务器(C2,Command & Control)通信**来实现。它的外联逻辑是一个**心跳循环**:

```text
   ┌────────────────────────────────────────────────┐
   ▼                                                 │
解密内置的C2域名 → 连接 → 上传窃取的凭据 → 接收指令 → 执行 → 睡一会 ──┘
   (域名在样本里是加密存放的,静态扫描扫不出明文)
```

两个设计要点:

- **域名加密**:C2 域名不以明文存在二进制里,运行时才解密 → 静态分析和字符串扫描看不到,增加溯源难度。
- **既偷又听**:回连不仅**上传偷到的账号密码**(盗号),还**接收远程指令**(这就是"后门"的本质)——攻击者随时可以下发下一阶段载荷,比如勒索。

### 8.2 本案真实 C2(脱敏 IOC)

| 域名 | 解析到 | 归属 | 状态 |
| ---- | ----- | ---- | ---- |
| `www.ic978y.com` | `154.198.50.139` | 🇭🇰 香港,AS138995 Antbox | 活跃(主用) |
| `gtrx.mpasoft.com` | —(当前 NXDOMAIN) | 母域托管在 Cloudflare 后 | 休眠(备用) |

> **杀软的分类**把这两个域名都标为"**木马盗号**",印证了"阶段一=窃取凭据"的判断。

### 8.3 防御逻辑与代码:网络层是最佳战场

C2 通信有一个对防御者极其有利的性质:**域名和 IP 是"全网共用、且不常更换"的 IOC**(跟"每台随机的服务名"恰好相反)。所以**网络层封堵 + 反查,是发现和切断整个攻击面最高效的一招**。

```powershell
# ── 用可信 DoH(Google)解析 C2 真实公网 IP,绕开本地可能被污染的 DNS ──
(Invoke-RestMethod "https://dns.google/resolve?name=www.ic978y.com&type=A").Answer

# ── 本机层面:在防火墙阻断与 C2 服务器的出/入站通信(各建一条) ──
New-NetFirewallRule -DisplayName 'BLOCK-C2-Out' -Direction Outbound -RemoteAddress 154.198.50.139 -Action Block
New-NetFirewallRule -DisplayName 'BLOCK-C2-In'  -Direction Inbound  -RemoteAddress 154.198.50.139 -Action Block

# ── 本机层面:用 hosts 把 C2 域名指向黑洞 ──
Add-Content "$env:windir\System32\drivers\etc\hosts" "`n0.0.0.0 www.ic978y.com`n0.0.0.0 gtrx.mpasoft.com"
```

**全网反查(在网关/DNS 服务器上做,效率最高):**

```text
在出口防火墙 / DNS 日志中检索:
   凡是解析过 ic978y.com / mpasoft.com、或连接过 154.198.50.139 的内网 IP
        = 其它中招主机名单
```

> **防御逻辑**:个体清除靠"行为特征",全网定位靠"网络 IOC"。**封堵 C2 域名/IP,既切断了正在中招机器的数据外泄,又能通过日志反查一次性圈出整个感染面。**

## 9 感染向量:下载劫持(MITM)——"感染网络"的根因

### 9.1 攻击逻辑

最初的疑问:用户说自己是从**飞书官网**下载的,怎么会中毒?排查样本发现一个反直觉的事实——那个 `Feish.exe` 是**字节跳动的正版有效签名**,并非伪造。

这指向一种比"假冒安装包"更高级的手法:

```text
用户 ──"我要下飞书"──▶ [被劫持的校园网] ──▶ 飞书官网
                            │ 在传输途中做手脚
                            ▼
        用户拿到:真·签名飞书(掩护) + 木马(夹带/侧加载)
        结果:飞书装好能正常用、签名也正常 → 用户和杀软都看不出异样
```

关键在于:攻击者**没有篡改飞书本体**(篡改会让签名失效),而是在**下载链路上夹带**。能在"从官网下载"这一步动手脚,只有网络层中间人(MITM)能做到,可能的劫持点:

| 劫持机制 | 原理 |
| ------- | ---- |
| DNS 劫持 | 把下载域名解析到攻击者服务器 |
| HTTP 篡改 | 下载走明文 HTTP 时,在途替换/夹带内容 |
| ARP 欺骗 | 某中招机冒充网关,劫持同网段流量 |
| 网关/路由被控 | 出口设备本身改写下载内容 |

### 9.2 为什么这是"感染网络"的根因

> **关键认知**:这不是"个别人被钓鱼",而是**网络基础设施在给所有人的下载投毒**。谁在这张网里下软件,谁就可能中招——这才解释了**全校大面积感染**。它的传播不靠蠕虫、不靠单封钓鱼邮件,而靠**对软件分发链路的污染**。

### 9.3 防御逻辑与代码

防御要从"信任链"入手——**不要默认信任下载下来的字节,要验证它的来源与完整性**:

```powershell
# ── 校验下载文件的数字签名是否有效、签名者是否为预期厂商 ──
$sig = Get-AuthenticodeSignature '下载的安装包.exe'
$sig.Status; $sig.SignerCertificate.Subject
# 注意:本案攻击者夹带的是"真签名飞书",所以"签名有效"还不够——
#       关键看【是否多出了不该有的文件/进程】【下载来源 IP 是否官方】

# ── 比对下载来源:用可信 DoH 解析官方下载域名,看本地解析是否被改 ──
$doh   = (Invoke-RestMethod "https://dns.google/resolve?name=<官方下载域名>&type=A").Answer.data
$local = (Resolve-DnsName '<官方下载域名>' -Type A).IPAddress
"DoH(可信): $doh"; "本地解析 : $local"   # 两者明显不一致 → 本地 DNS 可能被劫持

# ── 排查 ARP 欺骗:网关 IP 是否对应了异常/重复的 MAC ──
Get-NetNeighbor -AddressFamily IPv4 |
    Where-Object { $_.State -eq 'Reachable' -and $_.LinkLayerAddress } |   # 排除空MAC的不完整条目
    Group-Object LinkLayerAddress | Where-Object Count -gt 1              # 多个IP共用一个MAC=可疑
```

机构层面的根治手段(讲清逻辑,供讨论):

- **强制 HTTPS + HSTS**:明文 HTTP 才好被途中篡改;全站 HTTPS 大幅抬高 MITM 门槛。
- **可信 DNS / DNSSEC**:防止解析被污染。
- **终端只从官方源安装 + 校验哈希**:把"信任"建立在可验证的完整性上,而非"我点的是官网"。
- **网络准入与分段**:遏制 ARP 欺骗和已中招主机的横向影响。

## 10 应急响应方法论

前面九节是"点",这一节把它们串成"线"——一套可复用的应急流程。

### 10.1 核心思路:顺藤摸瓜

整个排查的灵魂,是不断追问**"它的上一级是谁"**,从可见的症状一路逆推到不可见的根:

```text
症状(随机bat反复出现)
  │ 谁在生成/执行它?  → 看父进程、看启动命令
  ▼
释放点(被某进程/服务反复拉起)
  │ 谁让它开机就在?   → 查 服务/计划任务/启动项/WMI
  ▼
持久化(SYSTEM 自启服务)
  │ 服务指向哪个文件? → sc qc 看启动路径
  ▼
本体(隐藏目录里的恶意程序)
  │ 它怎么进来的?     → 查下载来源、签名、文件创建时间
  ▼
入口(下载链路被 MITM 投毒)
```

### 10.2 标准六步(PDCERR 风格)

| 步骤 | 目标 | 本案对应动作 |
| ---- | ---- | ----------- |
| **准备 Prepare** | 工具、权限、取证环境就位 | 准备只读分析、管理员权限、样本隔离目录 |
| **检测 Detect** | 确认是否中招、范围多大 | 读杀软日志、查服务/进程/外联 |
| **遏制 Contain** | 阻止扩散与外泄 | 断网/隔离、封 C2、默认拒绝入站 |
| **根除 Eradicate** | 按正确顺序清除所有持久化 | 删服务→杀进程→删脚本→删本体目录 |
| **恢复 Recover** | 回到可信状态并验证 | 重启清内存 → 复查服务/bat/外联三归零 → 全盘查杀 |
| **复盘 Review** | 沉淀 IOC、堵住入口、形成文档 | 提取 IOC、修复下载链路、撰写报告 |

### 10.3 清除顺序铁律

> **面对"服务↔看门狗"互保结构,顺序错了等于白干。** 务必:
> **① 删服务(断复活源) → ② 杀进程 → ③ 删看门狗脚本 → ④ 删本体目录 → ⑤ 重启清内存 → ⑥ 重启后复查。**

### 10.4 取证纪律

- **先取证,后清除**:重装/删除前先保全样本与日志,否则无法溯源。
- **样本中性化**:拷贝样本后改扩展名(如加 `.sample`),绝不在裸机运行。
- **只读优先**:分析数据库/日志时以只读方式打开,避免污染原始证据。

## 11 本章小结

### 11.1 技术 × 检测 速查表

| 攻击技术 | MITRE | 攻击逻辑(一句话) | 防御抓手 |
| ------- | ----- | --------------- | ------- |
| 恶意服务持久化 | T1543.003 | 开机自启 + SYSTEM,服务名随机 | 查"cmd/c start"式 SYSTEM 自启服务 |
| 看门狗互保 | T1546 | 进程被杀就重启服务,死循环复活 | 查 C:\Windows 随机小bat;**先删服务** |
| 命令混淆 | T1027 | 字面打断、语义不变,骗过字符串匹配 | 先去混淆还原,再判读 |
| 进程注入 | T1055 | 寄生进正版进程,伪装外联来源 | Sysmon EID 8/10 + 异常进程外联;**重启清内存** |
| 父进程漂白 | T1134.004 | 让恶意进程"挂"在可信进程名下 | 可信进程突然生出脚本解释器=告警 |
| C2 加密心跳 | T1071/T1573 | 偷凭据 + 收指令,域名加密 | 网关/DNS 封堵与反查(最佳战场) |
| 下载劫持投毒 | T1557/供应链 | 真签名软件+夹带木马,污染分发链路 | HTTPS、可信DNS、哈希校验、来源比对 |

### 11.2 三条要记一辈子的认知

> 1. **杀症状不等于断根。** 反复发作 = 根还在。追根,别追症状。
> 2. **个体清除靠"行为特征",全网定位靠"网络 IOC"。** 随机名不可枚举,但 C2 域名全网共用。
> 3. **先用已知技术解释一切,排除干净再谈 0day。** 真 0day 极罕见,绝大多数"奇观"都是已知 TTP 的组合。

### 11.3 攻防的本质对照

```text
攻击者的两个字:  赖(持久化+互保)   藏(可信外壳+注入+混淆)
防御者的两个字:  根(按序断根)      痕(抓必留的行为/网络痕迹)
```

## 附:思考题与动手实验

### 思考题

1. 杀软显示"已处理",病毒却天天回来——用"症状 vs 根"解释这个现象。
2. 服务名是随机的,全网排查该用什么当 IOC?为什么 C2 域名比服务名好用?
3. 为什么"删完文件"还必须"重启"才算清干净?(提示:第 6 节)
4. 看到"恶意进程的父进程是浏览器组件",你的第一反应应该是"0day"还是"已知逃避技术"?为什么?
5. 攻击者用"真签名软件"做掩护,这一手击穿了哪几道常见防线(用户判断 / 签名校验 / 白名单)?

### 动手实验(全程安全,不碰真病毒)

> 在**你自己的电脑**上做,均为良性练习。

- **实验 A · 混淆还原**:把一段被插入符打断的良性命令(如 `e^c^h^o hello`)用 `-replace '\^',''` 还原,理解"为什么字符串匹配会漏"。
- **实验 B · 持久化的无害复现**:用管理员创建一个**良性**自启服务(让它启动计算器),再用 11.1 表里的检测命令把它找出来,最后 `sc delete` 清掉。一次性走完"持久化→检测→清除",全程无恶意代码。
- **实验 C · 日志取证**:用 Python `sqlite3` 打开一份系统/杀软日志,统计"被检出文件名、外联域名、父进程"的分布,体会"从日志反推攻击链"。
